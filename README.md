# columnar-compaction-store-go

一个纯本地文件模拟的列式数据存储组件（单 Go 包，零第三方依赖），提供：

- **列式写入与读取**：数据按列组织落盘；读取时只对用到的列发起磁盘读取（字节级列裁剪），并把简单过滤条件下推到段内逐行求值。
- **段级跳过（zone map）**：每个段文件自带列级 min/max 统计块；带过滤条件的扫描可整段跳过不可能命中的文件，统计缺失/损坏时安全回退完整扫描，绝不漏行。
- **小文件合并 + 一致快照读取**：多个小段合并为大段，清单原子交换；合并进行中的并发读者看到的永远是合并前或合并后的完整快照，绝不会看到半截结果；合并中途失败自动回到合并前状态。
- **表结构演进**：新增列 / 删除列 / 列改名 / 可兼容的类型变更（int64 → float64），新旧数据混读语义确定；不兼容变更被明确拒绝。
- **列生命周期身份稳定**：每列有单调的生命周期 ID。改名前后历史数据连续可读；删除后同名重生（哪怕类型完全不同）时，旧数据一律读成 NULL，老字节在任何读取方式下都不会被错位当成新值。
- **不静默容错**：列缺失、类型对不上、编码损坏（魔数/CRC/长度/非法值）都会返回可用 `errors.Is` 区分原因的错误。

## 1. 目录与落盘布局

一个 `Store` 对应磁盘上的一个目录（一张表）：

```
<store-dir>/
├── manifest.json               # 清单：结构历史 + 存活段列表（原子替换）
├── seg-0000000001.ccs          # 段文件（列式数据，不可变）
├── seg-0000000002.ccs
└── .seg-0000000003.ccs.tmp     # 正在写入/合并、尚未提交的临时段（崩溃即清理）
```

### manifest.json

```json
{
  "version": 7,                    // 清单单调版本，每次刷盘/合并/演进 +1
  "schema_history": [ {schema v1}, {schema v2}, ... ],
  "segments": [
    {"id": 2, "file_name": "seg-0000000002.ccs", "row_count": 100, "schema_version": 1}
  ],
  "next_segment_id": 3
}
```

- 清单以 `manifest.json.tmp` 写入 → `fsync` → `rename` 原子替换 + 目录 `fsync`，
  任何时刻磁盘上只有旧版或新版，不存在中间态。
- `schema_history` 保留所有历史结构版本；每个段记录它写入时的 `schema_version`，
  读取时先按旧结构解码，再映射到当前结构。

### 段文件二进制格式（大端序，当前写出 formatVersion=2，读取兼容 v1）

```
固定头 16 字节:
  magic[4]="CCS1" | formatVersion u16 | schemaVersion u32 | rowCount u32 | nCols u16
统计块（formatVersion >= 2 才有；段级跳过依据，与数据同文件同生命周期）:
  statsLen u32 | statsPayload | crc u32
  statsPayload: nEntries u16 | 每项: nameLen u8 | name | type u8 | min | max
列目录（nCols 项，让读取方无需触碰未用列）:
  nameLen u8 | name bytes | type u8 | frameLen u32
列帧（顺序与目录一致）:
  payload:
    nameLen u16 | name bytes      # 帧内自带身份，纳入 CRC，与目录交叉校验
    type u8 | count u32
    nullBitmap ceil(count/8) 字节  # 置 1 表示非 NULL
    values 按类型紧密排列           # int64/float64: 定长 8B；bool: 1B；string: u32 长度 + 字节
  crc u32                          # crc32-IEEE(payload)
```

- 读取列裁剪：读取方先读固定头 + 列目录（很小），按目录里的偏移只对投影列和过滤列
  发起 `ReadAt`，未用列的帧一个字节都不会从磁盘读取（有测试用计数 ReaderAt 证明）。
- 完整性：魔数、格式版本、目录长度、帧长度、文件长度、列名/类型/行数交叉校验、
  每帧 CRC32；任何损坏或截断都返回包装了 `ErrCorruptData` 的错误。
- 版本兼容：v1 是引入统计块之前的格式（固定头后直接是列目录），读取侧完整支持
  （见第 5 节）；写出侧永远写 v2。超出 [v1, v2] 范围的版本号报
  `ErrUnsupportedVersion` 而非 `ErrCorruptData`。

## 2. 写入与读取路径

- `Append(ctx, row)`：按**当前结构**校验后进入内存缓冲（行被规范化为只含声明列）。
  - 未声明列 → `ErrColumnNotFound`；Go 类型与列类型不符 / 非空列给 NULL → `ErrTypeMismatch`。
  - 缓冲达到 `FlushThreshold` 自动落段；也可显式 `Flush`。
- 落段：编码为列式字节 → 写 `.tmp` → `fsync` → `rename` 成正式段 → 原子更新清单。
- `Scan(ctx, ScanOptions{Columns, Filters})` 返回快照 `Scanner`：
  - 打开瞬间冻结段清单、当前结构与内存缓冲，并登记一个读引用；
  - 段按写入先后顺序读取，内存缓冲（最新数据）最后读取，因此行序等于写入序；
  - `Columns` 为空读全部列；`Filters` 为 AND 语义，支持 `== != < <= > >=`，
    NULL 对任何比较都不为真；过滤列即使未投影也会被加载；
  - `Next()` 耗尽时返回 `io.EOF`；`Close()` 释放快照引用。

## 3. 合并策略与一致读取

选段规则（`pickCompactionSegments`）：

1. 存活段数 ≥ `CompactionMinSegments`：合并**全部**段（全量合并，语义最简单、
   结果最确定）；
2. 否则当 `CompactionTargetRows > 0` 且存在 ≥2 个行数低于目标的小段：合并这些小段；
3. 其余情况（不足 2 段）不动作。

合并流程（`Compact`）：

1. 先刷盘内存缓冲；选出待合并段。
2. 把旧段按**当前结构**读出（自动应用类型提升），编码写入一个全新段
   `.tmp → rename`（此期间没有任何读者知道新段）。
3. 在互斥锁内一次性把清单的存活段集合替换为新段，并原子持久化清单。
4. 等待所有持旧快照的扫描器 `Close`（WaitGroup 计数）后，才物理删除旧段文件。

由此得到的保证：

- **快照一致性**：扫描器在读锁内取快照，清单交换对它要么已发生要么未发生；
  旧段文件在最后一个旧扫描器退出前不会被删除，因此读者永远读不到"合并到一半"
  或已被删除的文件（并发测试用每段 1 行、40 段、12 个持有快照的读者反复验证）。
- **崩溃恢复覆盖三个时间窗口**（重启后都必须回到一致状态，不出现行数对不上、
  半截数据、重复行或残留文件被当成有效数据）：
  1. 新段写完之前（`.tmp` 阶段）崩溃：临时文件被清理，状态 = 合并前；
  2. 新段已完整落盘、清单尚未交换时崩溃（故障注入点 `compactFailAfterCommit`）：
     清单仍引用旧段，无主的新段文件被清理，状态 = 合并前，合并可重试成功；
  3. 清单已交换、旧段未及删除时崩溃（故障注入点 `compactFailAfterSwap`）：
     清单只引用新段，旧段作为无主文件被清理，状态 = 合并后。
- **失败回滚**：交换前任一步骤失败 → 删除新临时段，内存与磁盘清单保持旧状态，
  旧段原封不动，重试合并可成功（故障注入点 `compactFailBeforeSwap` 覆盖）。

## 4. 表结构演进与兼容规则

每次演进 `version + 1` 并整体追加到 `schema_history`（旧结构不可变）：

| 变更 | 是否允许 | 读写语义 |
| --- | --- | --- |
| 新增列 | 仅允许 **Nullable** 列 | 旧行该列读出为 NULL；非空新列会让旧数据无法填值，直接拒绝 |
| 删除列 | 允许 | 旧段里的物理字节保留但永不加载、永不出现在结果行 |
| 列改名 | 允许（新名不得与现有列重名） | 生命周期 ID 不变，改名前后历史数据在新名字下连续可读；旧名字立即失效（按旧名投影/过滤报 `ErrColumnNotFound`） |
| 同名重生（删除后同名再增） | 允许，类型可完全不同 | 新列分配全新生命周期 ID；旧数据上该列读 NULL，老字节永不错位当成新值，整表读取不受类型不兼容影响 |
| int64 → float64 | 允许 | 读旧段时把 int64 无损提升为 float64；合并后以 float64 重写 |
| 同类型改同类型 / 同名改名 | 幂等 | 不产生新版本 |
| 其它跨类型变更（string↔int64、float64→int64、bool↔* 等） | **拒绝** | 返回 `ErrIncompatibleSchema`，绝不按字节错位解释 |

### 列的生命周期身份

每列在创建时分配单调递增的 **生命周期 ID**（记录在 `schema_history` 与清单
`next_column_id` 中），段文件里存的是列名，但读取时先按"段写入时的结构版本"
把存储列名解析成 ID，再映射回当前结构：

- **改名**：ID 不变，旧段的 `status` 帧被映射到新名 `state` 下解码，历史连续；
- **同名重生**：新旧两列 ID 不同，旧段的老列解析不到当前任何列 → 直接跳过不加载，
  新列在旧数据上补 NULL。带列裁剪与不带列裁剪走同一条解析路径，结果必然一致；
- 清单里 ID 为 0（升级前老库或手工构造的清单）时退化为按名称匹配的旧行为；
  打开老库时会一次性归一化补齐 ID（见第 5 节）。

- 演进入口：`AddColumn` / `DropColumn` / `RenameColumn` / `AlterColumnType`；
  演进前会强制刷盘，保证"哪一行按哪个结构写入"的边界落在段边界上。
- 段写入时记录结构版本；读取时若发现存储类型无法安全转换到当前声明类型，
  返回 `ErrIncompatibleSchema`（含列名与两种类型），而不是猜着解码。

## 5. 老版本兼容与升级策略

本节回答一个问题：**升级前那一版写出的存储目录，用当前代码打开会怎样。**

### 老库直接可读，无需迁移

升级前的版本写出的是 **段格式 v1**（固定头后直接是列目录，无统计块）+
**无列生命周期 ID 的清单**。当前代码打开这种目录后：

- **全部读取路径照常工作**：全列读、列裁剪读、带过滤读、关闭重开，
  读到的行数与取值与升级前完全一致（兼容性测试用升级前版本真实写出的
  `testdata/legacy-v1` 逐行断言）；
- **过滤读自动降级**：v1 老段没有统计块，段级跳过判定按"统计缺失"处理，
  静默退回完整扫描——结果绝不少行，只是不享受跳过加速；
- **可以继续在线用**：追加新行（落 v2 段，与老 v1 段混读）、触发合并、
  做结构演进，都不丢、不重、不错老数据；合并会把老段重写成 v2
  （老值原样保留，同时获得统计块），此后过滤读即可享受段级跳过。

### 打开时的一次性归一化

`Open` 检测到清单来自升级前版本（存在 ID 为 0 的列或缺少 `next_column_id`）时，
会在内存中补齐列生命周期身份并**原子落盘**（走与一切清单写入相同的
`.tmp + fsync + rename` 路径，清单版本 +1）：

- 按结构版本顺序扫描，**同名列共享同一个生命周期 ID**——这精确保持旧版
  "按名匹配"的读取语义，老段字节在升级前后的读法逐行一致（包括老库历史上
  发生过的同名重生）；
- 归一化是**幂等**的：再次打开不会改写清单；
- 归一化只动 `manifest.json`，**不碰任何段文件**；
- 归一化之后，改名/删列再加列都走 ID 语义：改名后老数据在新名字下连续可读；
  升级之后新发生的同名重生分配全新 ID，老字节读 NULL（第 4 节的新语义）。

注意：`Open` 需要目录可写（归一化要落盘清单）；只读目录上的老库会在打开时
返回归一化落盘失败的错误，而不是静默给出不一致的读法。

### 真正不兼容时的行为

- 段文件格式版本超出本代码可读范围（当前为 [1, 2]，例如来自更新实现的 v3）：
  **`Open` 时即失败**，错误可断言为 `ErrUnsupportedVersion`，并指明是哪个段、
  版本号是多少。它**不是** `ErrCorruptData`——"版本不兼容"与"文件被改坏"
  是两类可区分的原因，前者不会伪装成后者，也不会拖到扫描中途才暴露、
  更不会只读出一半就当成功；
- 为此 `Open` 会校验全部存活段的文件头与列目录（不读列帧，开销可忽略）：
  头部损坏同样**在打开时**报 `ErrCorruptData`；列帧内部的字节损坏仍在
  扫描到时照常报 `ErrCorruptData`（CRC 保护），与版本问题严格可分。

## 6. 段级跳过（zone map）与回退策略

每个段文件自带一份列级 min/max 统计块（编码段文件时从真实行计算，与数据同文件、
同生命周期，受 CRC 保护；合并重写段时同样重新计算，因此统计与数据天然一致）。

带过滤条件的扫描在读取数据帧之前先评估统计块：任一过滤条件（AND 语义）对该段
所有行必然为假时，整段跳过——一个数据帧都不读，只读固定头 + 统计块 + 列目录。
列裁剪照常生效，与跳过互不干扰。跳过判定覆盖 `== != < <= > >=` 六种操作符，
并处理两类身份场景：过滤列在段写入后新增（该段全 NULL，必然不命中，直接跳过）；
列改名后按生命周期 ID 找到老名字下的统计继续生效。

安全回退（宁可多读，绝不漏行）：

- 统计块缺失、CRC 错、编码损坏、min>max、统计类型与过滤值类型不一致
  （如 int64→float64 演进后的旧段）：一律当作无统计，退回完整扫描；
- 统计只覆盖非 NULL 值（NULL 对任何比较都不为真，不影响跳过判定）；
- 含 NaN 的列不生成统计；全 NULL 列没有统计项，自然不跳；
- 回退是静默的：统计只是跳过依据，绝不作为错误上抛，也绝不影响结果正确性。

## 7. 可断言区分的错误

```go
errors.Is(err, ErrColumnNotFound)      // 列不存在 / 行里出现未声明列
errors.Is(err, ErrTypeMismatch)        // 值类型不符 / 非空列 NULL / 过滤值类型不符
errors.Is(err, ErrCorruptData)         // 段文件魔数/CRC/长度/编码损坏或段文件缺失
errors.Is(err, ErrIncompatibleSchema)  // 不兼容的结构变更或存储类型无法演进
errors.Is(err, ErrManifestCorrupt)     // 清单 JSON 损坏或内容不自洽
errors.Is(err, ErrUnsupportedVersion)  // 段格式版本超出可读范围（打开时即报，非损坏）
errors.Is(err, ErrNotFound)            // 目录未初始化
errors.Is(err, ErrClosed)              // Store/Scanner 已关闭
```

扫描结束：`errors.Is(err, io.EOF)`。

## 9. 快速上手

```go
s, _ := columnar.Create("./data", columnar.Schema{Columns: []columnar.Column{
    {Name: "id", Type: columnar.TypeInt64, Nullable: false},
    {Name: "name", Type: columnar.TypeString, Nullable: true},
}}, columnar.DefaultOptions())
defer s.Close()

_ = s.Append(ctx, columnar.Row{"id": int64(1), "name": "alice"})

sc, _ := s.Scan(ctx, columnar.ScanOptions{
    Columns: []string{"name"},
    Filters: []columnar.Filter{{Column: "id", Op: columnar.OpGreaterEqual, Value: int64(1)}},
})
defer sc.Close()
for {
    row, err := sc.Next()
    if errors.Is(err, io.EOF) { break }
    // row == {"name": "alice"}
}

_ = s.AddColumn(ctx, columnar.Column{Name: "tag", Type: columnar.TypeString, Nullable: true})
_ = s.Compact(ctx)
```

## 设计边界（有意为之的简化）

- 单表/单目录、行全在内存缓冲、解码结果在扫描器内物化（演示组件，不做流式执行）。
- 合并为全量或小段合并，不做 Size-Tiered/Leveled 等复杂策略。
- 类型系统仅 int64/float64/string/bool；可兼容转换仅 int64→float64。
- 段文件格式当前为 v2（固定头后新增统计块）；不承诺读取更老版本的段文件。
- 无后台线程：刷盘与合并由显式调用/阈值触发，行为完全确定、可测试。
